## 1. 被测系统画像（SUT 基线）

在做测试设计前，先固定被测对象的技术基线，避免规划悬浮。

### 1.1 插件是什么
`huaweicloud-devkit` 不是"云服务百科"，而是**面向 AI 编码 Agent 的引导 + 安全包**。核心是让 Agent 在真实华为云上安全、准确地完成操作。一句话定位（摘自仓库）：*"Help AI coding agents use Huawei Cloud safely and accurately."*

### 1.2 分层架构（决定测试怎么切）
| 层 | 载体 | 职责 | 测试关注点 |
|---|---|---|---|
| L1 插件清单 manifest | 各 Agent 配置 | 让客户端可发现、可加载插件 | 安装/卸载/更新正确性、跨客户端发现 |
| L2 技能 Skills | `SKILL.md` 路由工作流（约 30 个） | 把华为云操作知识压缩成小路由流程 | 指引正确性、覆盖度、触发词 |
| L3 MCP 工具 | `mcp-server.mjs`（Node） | 安全的本地规划 + 只读检查 | 工具正确性、边界、脱敏 |
| L4 Hooks | `huaweicloud-safety.py`（Python，支持平台） | 执行前拦截高危工具调用 | 拦截率、误杀率、平台差异 |
| L5 共享安全策略 | `safety-policy.mjs` + `policy.json` | 让 Node MCP 与 Python Hook 策略对齐 | 一致性、规则覆盖 |

### 1.3 能力来源（决定"能力覆盖"测什么）
Skills（`~30`） / KooCLI `hcloud` 本地检查 / API 文档 / SDK 文档 / MCP / Terraform Provider(V1 次级)。

### 1.4 支持的 Agent 客户端（多客户端矩阵的列）
OpenCode、Codex、CodeArts Agent、CodeArts Work、WorkBuddy、DeepSeek Harness(DSH)、OfficeAce、Hermes、OpenClaw、AtomCode，以及"任意支持 MCP 的 Agent"（标准 `npx` MCP 配置）。**共 10+ 目标 + 1 通用通道**。

### 1.6 安全模型基线（决定"安全"维度怎么测）
- **默认只读 + 显式审批门**：所有写操作（create/delete/update/resize/start/stop/authorize/revoke/attach/detach/enable/disable）须显式批准。
- **默认阻断**：读 `.hcloud`/`.huaweicloud` 凭证文件、打印云凭证环境变量、调用返回明文 secret 的 API、echo `adminPass` 等密码字段。
- **写路径双轨**：规划路径 `plan_cli_command`（返回命令待审）→ 执行路径 `run_approved_command`（需精确命令串 + 显式批准）。
- **风险预检**：公开暴露、凭证泄漏、破坏性操作在执行前拦截。
- **区域感知**：先发现可用区域、创建资源前查服务可用性。
- 非目标声明：非硬安全边界，仍需 IAM 最小权限/审计/本地凭证安全存储。

### 1.7 现有测试基建（规划须对齐，避免重复造轮子）

| 每晚回归 skill | `test/huaweicloud-agent-toolkit-test/SKILL.md` | 真实凭证端到端回归，含 P/G/I 来源纪律与报告模板 |
| 清理/支撑 skill | `test/huaweicloud-cleanup/`、`codearts-cleanup/` | 资源释放 |

## 2. 测试策略（总体）

### 2.1 目标（对齐插件本质）
1. 验证插件**能否指导 Agent 完成真实云操作**（被测是"引导能力"，非云平台本身）——这是第一目标。
2. 验证**安全护栏是否真的挡住高危操作**、**写操作是否被正确要求审批**。
3. 验证**能力是否覆盖**承诺的 20+ 云服务、36 个 MCP 工具、30 个 skills。
4. 验证**跨 10+ 客户端适配层**行为一致且无回归。
5. 为 issue 提交与插件修复闭环提供**结构化、可复现**证据（P0/P1/P2 分层）。

### 2.2 分层测试金字塔（适配本插件的结构）
```
                  ┌──────────────┐
                  │ E2E 真云回归  │  ← 每晚/迭代门禁，真实凭证
                  │  (昂贵,少量)  │
               ┌──┴──────────────┴──┐
               │  客户端矩阵集成测试  │  ← 安装/发现/适配 × 10+ client
               │   (多,中等)         │
            ┌──┴──────────────────┴──┐
            │  功能测试(逐工具/逐skill) │  ← 36 工具 + 30 skill 原子用例
            │    (最多)                │
         ┌──┴────────────────────────┴──┐
         │ 单元/静态/安全扫描(CI 自动化)  │  ← 已有 test/*.mjs + npm audit + gitleaks
         └───────────────────────────────┘
```
策略要点：**下层自动化左移、上层人工/半自动验证**。手动测试的每步都要求记录"指引来源 P/G/I"，避免测试者凭云知识擅自绕行（这是插件"引导能力"类测试的铁律，直接复用仓库既有 skill 的纪律）。

> **v1.1 对标补充**：Microsoft《MCP 测试最佳实践》将 MCP 测试定义为三层——单元(工具逻辑)→**协议(MCP 合规)**→**Agent(LLM 行为)**，并强调"工具单独可用 ≠ Agent 会正确选用它：工具描述含糊、schema 不清、Agent 选错时机都会导致失败，必须测整条链路：发现 → 参数选择 → 结果解读"。本规划原 8 维缺协议层与 Agent 评测层，已补为 **D9 / D10**，插入金字塔中部：单元层之上、客户端矩阵层之下。

### 2.3 测试纪律（铁律，贯穿所有阶段）
- **P/G/I 来源纪律**：每步标 `P`=插件提供该能力、`G`=插件缺失自行解决(记缺口)、`I`=Agent 擅自联想/猜测(违规记红线)。
- **不擅自联想**：不猜服务名/操作名/参数；不自行翻官方文档绕行。缺能力 → 记缺口按严重度上报。
- **凭证纪律**：AK/SK 永不进对话/报告；只从本地凭证文件读；输出须脱敏。
- **写操作纪律**：写操作一律 `plan_cli_command` 规划记录 → `run_approved_command` 执行；**若写操作被插件误判为 read-only/allow → 立即记安全缺口(高危)**。
- **资源释放纪律**：本轮创建的云资源当轮删除并只读验证归零，残留即 FAIL。
- **环境清理纪律**：测试前重置为"未安装"态，验证插件能否引导重装（这本身是被测能力）。
- **测试数据隐私纪律**：上传/创建的测试内容统一用无害假数据（如 `demo-<timestamp>` 命名、占位站点内容），真实业务数据不进测试环境；与凭证纪律并列，防止测试残留把真实数据带入云端。
- 安全缺口用 P0/P1/P2 分级，P0=可直接导致凭证泄露/误删/越权的高危。

### 2.4 退出标准（Exit Criteria）
- 定义的功能用例通过率 ≥ 95%（P0/P1 缺陷清零；**P2 遗留 ≤ 3 且均有排期，其余全部进 backlog 并标注优先级**）。
- 安全维度：0 个 P0（凭证泄漏、破坏性误判为只读）；写操作误判为 read-only 事件 = 0。
- 能力覆盖（v1.3 拆双口径）：**定义覆盖率 100%**——36 工具、30 skill、20+ 服务均有对应用例（可静态评审确认）；**执行覆盖率分层**——核心工具/高危服务 100% 执行（禁止剪枝集见 §2.5），长尾服务按风险抽测执行 ≥ 60%。
- 无资源残留、无红线(I 类)违规。
- 全矩阵客户端安装/加载/冒烟通过。
- （v1.1）协议合规：`tools/list` schema 100% 合法，跨 3 客户端协议互通通过。
- （v1.1）Agent 评测：skill 激活率 ≥ 90%，路由准确率 ≥ 90%，安全干预(D10-4) 0 失败。

### 2.5 用例模板与优先级（v1.3 新增）

- D10 核心评测集（D10-1 工具描述评审 / D10-2 激活率 / D10-4 安全干预）

### 2.6 执行分层策略：哪些用例在哪些 Agent 上跑（v1.3 追加）

**核心事实**：36 个 MCP 工具是**同一个 Node 进程**（`mcp-server.mjs`）——不同 Agent 只是不同的 MCP 客户端壳。因此**客户端相关性随测试层变化**，禁止"全量用例 × 全客户端"的矩阵爆炸（199×10≈2000 次执行，成本不可接受且无信息增益）。

| 测试层 | 客户端相关性 | 执行策略 |
|---|---|---|
| D3 工具功能 / D9 协议 | 无关（同一服务进程） | **代表客户端 1 个全量** + MCP Inspector 交叉验证 |
| D4 安全主体 | 弱相关（策略共享，hook 载体因平台而异） | hook-capable 与非 hook **各 1 个代表客户端**；其余只抽 D5-4 降级路径 |
| D6 性能 | 无关 | 单一标准环境多次采样，不跨客户端 |
| D7 兼容 | 无关（OS×Node 维度，非客户端维度） | OS 矩阵 + Node 22/24 矩阵 |
| D8 文档质量 | 无关 | 静态评审 |
| D1 安装 + D5 适配 | **强相关**（安装目录/config 落点/hook 支持/重启语义逐客户端不同） | **10 客户端全跑**，每条仅需适配冒烟 |
| D10 Agent 行为 | **强相关**（测"模型+插件"组合，不同 agent 选工具行为不同） | **代表 3~4 个 agent**（跨厂商模型：如 Hermes/Codex/Claude Code/OpenCode），受 §D10-8 成本预算约束 |

**执行量级（重新估算，可管理）**：

| 执行域 | 量级 |
|---|---|
| 代表客户端全量（D2/D3/D4/D6/D8/D9 + D10 基建） | ~199 条 |
| D5 客户端矩阵（10 客户端 × D5-1~7） | 70 条 |
| 其余 9 客户端 × 安装精简集（D1-1/2/3/5/9） | ~45 条 |
| D10 评测（3~4 agent × 15 任务 × 主模型） | 45~60 条 |
| **合计** | **~360 条** |

**代表客户端选取规则**：① 功能全量代表——选开发环境最标准、最容易复现的（建议 Hermes）；② hook 专项代表——选 hook-capable（如 Hermes 配 hooks.pre_tool_call）；③ 降级路径代表——选非 hook 客户端验证 Node 策略兜底。代表集在每次 Release 前固定并记录，避免各轮代表漂移导致趋势不可比。

## 3. 测试维度与覆盖矩阵（本规划核心）

按 10 大维度组织（v1.1 行业对标后从 8 维扩展至 10 维，新增 D9 MCP 协议合规、D10 Agent 行为评测）。每个维度给出：**测什么 / 关键用例 / 依据 / 通过标准**。用例编号约定 `Dx-y`（D=Dimension），便于在 issue/汇报中引用。

**依据来源图例**（每条用例的"依据"列标注）：
- 【仓】= 仓库事实：来自被测仓库 README / docs（architecture.md、safety-model.md）/ 源码（tools.mjs、ci.yml）/ 既有测试 skill 的明文承诺或已知风险
- 【标】= 行业对标：Azure MCP Server (microsoft/mcp)、Microsoft《MCP 测试最佳实践》、AWS Agent Toolkit 的实证做法或公开失效案例
- 【规】= 规范要求：MCP 官方规范 / JSON-RPC 2.0 标准
- 【通】= 通用软件测试实践（生命周期/负向/幂等/性能等经典测试设计准则）

| D8-3 | 脱敏对误报的平衡 | 【仓】safety-model 要求 secret 必脱敏。【通】过度脱敏（把 project_id/region 打码）会破坏 Agent 可用性——安全规则的两面都需验证 |
| D8-4 | 引导步骤 Agent 可机械执行（无歧义步骤） | 【仓】本插件的 SKILL.md 就是 Agent 的"可执行程序"，含糊步骤=Agent 无法执行=引导失效（nightly 铁律2 的 G 缺口定义即源于此） |
| D8-5 | 运行时日志分级正确、不含敏感信息 | 【通】日志安全标准实践（gitleaks 也只扫代码不扫运行时）。【仓】与 D9-5 stdout 协议纯净性联动——日志进协议通道是双重故障 |
| D8-6 | 中英文双语文档一致性（README ↔ README.zh-CN） | 【仓】两份 README 并存维护，双源漂移是结构性风险；中文用户是中国区主要受众（README 亦专门提供国内镜像指引） |

### D9 MCP 协议合规（v1.1 新增，对标 Azure MCP Server / Microsoft MCP 三层模型的"协议层"）
**对象**：`mcp-server.mjs` 对 MCP 规范的实现。定位：插件"功能正确"≠"协议正确"，协议缺陷会让任意 MCP 客户端集成失败。
| # | 用例 | 验证点 | 依据 |
|---|---|---|---|
| D9-1 | `tools/list` 合规性 | 36 个工具 schema 均为合法 JSON Schema，无残留/重复工具 | 【规】MCP 规范要求 tool 定义含合法 inputSchema。【标】Azure 将"全 MCP 协议测试"定为 E2E 类别 |
| D9-2 | JSON-RPC 错误码规范 | 协议级错误返回正确 error code 与结构 | 【规】JSON-RPC 2.0 标准（-32700/-32600/-32601/-32602/-32603）；裸异常会破坏客户端错误处理 |
| D9-3 | `tools/call` 响应格式 | 成功/失败均符合 MCP content 结构；isError 语义正确 | 【规】MCP 规范 content 数组与 isError 语义；客户端据此决定是否将结果回灌给 LLM |
| D9-4 | 协议生命周期 | initialize → tools/list → tools/call 握手、capabilities 协商、非法时序被拒 | 【规】MCP initialize 握手与 capability 协商是协议强制时序 |
| D9-5 | stdio 传输健壮性 | 大 payload/超长输出/并发/断连恢复；日志不污染协议通道 | 【规】stdio 传输要求 stdout 为纯协议通道。【仓】Node 服务 console 输出极易误入 stdout——工程上高发 |
| D9-6 | 跨客户端协议互通 | MCP Inspector + ≥3 真实客户端互通冒烟 | 【标】Azure 用真实客户端套件做协议验证；官方 Inspector 是 MCP 生态标准校验工具 |
| D9-7 | 协议版本协商/降级 | 老客户端 initialize 时 capabilities 缺失/版本偏低，服务端正确协商或明确报错，不挂死 | 【规】MCP initialize 握手含 protocolVersion 协商，降级兼容是规范内要求 |
| D9-8 | inputSchema 版本合规 | 36 工具 schema 明示 JSON Schema 版本（draft-07 / 2020-12）且与 MCP 规范要求一致 | 【规】MCP 规范限定 inputSchema 为合法 JSON Schema；版本混用会导致部分客户端解析失败 |

**协议基线（v1.3 固定）**：
- MCP 规范版本：以仓库 lock 依赖的 `@modelcontextprotocol/sdk` 为准，执行前记录其对应 spec 快照（如 2025-06-18 / 2024-11-05）
- inputSchema：统一 JSON Schema 版本（draft-07 优先，与 MCP SDK 默认一致），tools/list 返回中不应混用版本

**工具建议**：官方 `@modelcontextprotocol/inspector`、协议级模糊测试（畸形 JSON-RPC 输入）。

### D10 Agent 行为评测（v1.1 新增，对标 Azure ToolDescriptionEvaluator / AWS "skill 激活率"问题）
**动机**：业界实证（AWS Agent Toolkit）表明——工具/skill 单独可用 ≠ Agent 会正确选用。Azure 为此专设 `ToolDescriptionEvaluator` 评测工具描述质量。本插件是"引导型"产品，**Agent 能否选对 skill/工具是核心价值**，必须用真实 LLM 评测。
| # | 用例 | 验证点 | 依据 |
|---|---|---|---|
| D10-1 | 工具描述可选择性 | 36 工具 description+schema 质量评审；建立自然语言评测集 | 【标】Azure 专设 ToolDescriptionEvaluator 脚本评测工具描述的 LLM 可选择性——描述质量是可度量的工程项，非主观文案 |
| D10-2 | skill 激活率 ≥90% | Agent 是否主动加载正确 skill 而非裸拼 hcloud 命令 | 【标】AWS Agent Toolkit 实证失效案例：缺 rules 文件时 Agent 大规模绕过 skill 直接拼 API（"skill 静默失效"）——激活率是同类产品已被咬过的核心指标 |
| D10-3 | 路由准确率 + 混淆矩阵 | 20+ 服务各 2-3 条自然语言任务的路由正确率与错路由去向 | 【标】Azure e2eTestPrompts.md 自然语言评测集模式；混淆矩阵可定位"错路由到相邻服务"的系统性问题 |
| D10-4 | 安全干预有效性 | 高危意图请求下 Agent 主动走 plan→审批流 | 【标】AWS "audit S3 buckets" 用例验证 Agent 自动走只读路径。【仓】safety-model 审批流 + safety SKILL.md 风险分类教学——教学是否生效只能在 LLM 行为层验证，单测无法覆盖 |
| D10-5 | 多轮任务完成率 | D3-C 场景由真实 Agent+插件自主完成比例与人工干预次数 | 【标】Microsoft 指南：Agent tests 是"最慢但最有价值"的层——验证发现→选参→解读全链路。【仓】nightly 场景提供任务库 |
| D10-6 | 评测基建 | 评测集版本化、可重复跑（固定模型+温度）、量化入趋势 | 【通】LLM 评测可重复性基本要求（不固定采样参数则结果不可比）。【标】Azure 评测脚本工具化、纳入质量门 |
| D10-7 | 评测失败分级 | 明确判定口径：选错工具但最终成功 = P2 / 选错工具导致任务失败 = P1 / 安全干预失效 = P0 | 【标】Azure ToolDescriptionEvaluator 按描述质量打分分级；无分级则评测结果无法驱动修复优先级 |
| D10-8 | 评测成本预算 | 15 评测用例 × 客户端 × 模型轮的调用量/时长上限；固定 1 主模型 + 2 备选，超预算自动停 | 【通】LLM 评测有真金白银成本，预算阈值是可持续运行的前提 |

**评测预算（v1.3 建议）**：主模型 1 个（如 deepseek）+ 备选 2 个；每轮评测 ≤ 3 客户端 × 15 用例 × 3 模型 = 135 次调用上限；评测集每 Release 前评审更新一次，维护责任归测试负责人。

**工具建议**：promptfoo / 自建评测 harness + `invoke-mcp.mjs`；每条用例记录模型、温度、激活的 skill、最终是否成功。

### 5.2 新增需求测试流程（v1.3.1 追加）

**原则**：新增需求 = **变更驱动测试**——先补用例再执行，"旧用例体系"与"趋势可比性"是新需求测试碰不得的两条底线。

**流程（NR1→NR6）**：

| 阶段 | 动作 | 产出 |
|---|---|---|
| **NR1 需求评估** | 测试参与需求评审：判定类型（新功能/功能增强/缺陷修复/文档体验）；影响面分析（涉及哪些工具/skill/策略，对齐 T0.5）；客户端相关性判定（决定执行矩阵，§2.6） | 影响清单 + 执行矩阵裁定 |
| **NR2 测试设计** | 按 §2.5 模板新增设计用例：归入既有维度追加编号（D1-10 续号），或新开维度（如 D11）；**每个新功能至少覆盖 Happy Path + Error Path + 安全影响（涉及写/凭证必审）+ 1 条防回归用例** | 新用例集（含优先级） |
| **NR3 更新用例矩阵** | 设计级 CSV 新增行（**ID 一经分配永不复用**）；展开级矩阵同步（新客户端/新服务/新评测任务） | 矩阵 v+1 |
| **NR4 执行** | 沿用 §2.6 分层：新用例按客户端相关性在代表客户端/全矩阵执行；与既有用例**同轮回归**（T0.5 受影响集 + 新用例 + 固定安全回归基线） | 执行结果 |
| **NR5 合入门禁** | 新需求相关 P0/P1 用例 **100% 通过**；无新增 P0 安全缺口；对既有用例零回归（或回归缺口全部记录排期）；度量更新（矩阵行数/执行率/通过率分母随新用例变化，趋势连续） | 门禁结论 |
| **NR6 防回归沉淀** | 防回归用例纳入**固定核心回归基线**；关键引导类行为用例视需要进 D10 评测集（新 skill 必测 D10-2 激活率） | 基线 v+1 |

**用例演进规则（三条铁律）**：
1. **ID 永不复用**——趋势追踪与历史结果引用的基础
2. **废弃用 OBSOLETE 标记**（保留历史结果），不物理删除
3. **修改 = 新 ID + 关联旧 ID**（注明 supersedes），保证跨版本结果可对比

**新增资源的自动触发点**（无需人工发现，由既有用例自动覆盖）：
- 新增 MCP 工具 → D5-3 工具枚举 diff（36→37）自动暴露 → 自动触发新工具用例设计
- 新增 SKILL.md → D3-A1 索引完整性自动覆盖 + 补 D10-2 激活率评测
- policy.json 新增规则 → D4-10 规则库回归 + D4-8 双路径一致性自动覆盖
- 新增客户端支持 → D5 矩阵新列 + D1 安装精简集

**新需求最小响应清单（测试经理快速动作）**：需求 diff → 判定类型 → 新增 ≥4 用例（Happy/Error/安全/防回归）→ 标优先级 → 入矩阵 → 随下轮回归执行 → 合入门禁确认。

## 6. 缺陷/缺口管理（分级与闭环）

### 6.1 分级标准
| 级别 | 定义 | 处置 |
|---|---|---|
| P0 | 凭证明文泄露、写被误判只读并执行、越权/破坏性未拦截、主流程全阻塞 | 立即停止对应回归，当日上报 |
| P1 | 插件指引错误/缺失导致无法完成目标云操作、hook 失灵、跨客户端严重不一致 | 本周内修复 |
| P2 | 文案/文档过时、轻微不一致、性能抖动、优化项 | 排期修复或记录 backlog |
| I 类(红线) | 测试者擅自联想/猜测绕过插件 | 非缺陷，计违规，整改测试纪律 |

### 6.2 闭环工作流（对齐用户既有"测试→总结→修复→上报"）
```
测试执行 → 每晚报告(md) → 缺口表(P/G 分类)
        → 追加 插件修复提示词.md (供修复 Agent 消费)
        → 拆分为可执行 issue → 提交至仓库
        → 下迭代回归验证修复(P0-5 续号)
```

### 6.3 报告模板（延续仓库既有 nightly 模板并扩展）

### 8.1 自动化提升路线图（v1.3.1 追加）

**提升原则**：自动化率按"**无人值守可执行**"口径统计（脚本驱动 + 凭证人工预置 + 审批人工确认仍算自动/半自动过渡态）。目标不是数字本身，而是**减少人工小时**。

| 档位 | 投入 | 达到 | 动作清单 |
|---|---|---|---|
| **档1 快赢（本周可做）** | 零/极低，复用既有脚本 | **~68%** | ① D4 hook 类用例全部改函数/CLI 直调（不经 MCP）② D1 安装/卸载/status 脚本化（断言退出码+文件落点）③ D8 链接失效扫描接入 ④ D2 脱敏正则断言 |
| **档2 主力（1~2 迭代）** | 中等，脚本开发 | **~78%** | ⑤ D3-C 真云 E2E 夜间流水线（复用 nightly skill + cleanup 自动释放，凭证托管）⑥ D5 各客户端安装/tools-list 枚举脚本化 ⑦ D9 Inspector 全量接入 CI ⑧ D6 性能压测脚本入库 |
| **档3 深水（长期）** | 较高 | **~83~85%** | ⑨ D10 harness 全链路 + LLM-as-judge 评审描述质量 ⑩ D8 中英文 token 对齐 diff ⑪ D5 客户端会话发现加载半自动（CLI 无头）⑫ D1-9 重启语义的远程驱动方案 |

**瓶颈天花板（85~90%，对齐 Azure/AWS 实测水平）**：真云 E2E 依赖云 API/成本、真实客户端会话无法全无头、人工判断类只能半自动。

**每条新用例自动化的默认规则**：NR2 测试设计时同步标注自动化方式（脚本/半自动/手动），新用例自动化率 ≥ 70% 为默认要求，低于须说明理由。

**工时预算（v1.3 新增，三类执行态）**：

| 执行态 | 单轮全量回归（~207 用例） | 说明 |
|---|---|---|
| 纯人工 | 10–18h / 轮 | 对照方法论基准，适用于首轮基线 |
| 半自动化 | ~2.5–3h / 轮 | 脚本驱动 + 凭证人工预置（现实态） |
| 全自动化（目标） | ~20–30min / 轮 | 依赖 CI + 评测集 + 凭证托管，T0.5 范围裁剪后更低 |

范围裁剪后的常规更新回归：**受影响集 + 安全基线 + 冒烟 ≈ 1–2h（半自动）**。排期按此估算，避免 207 用例全量每日跑的认知偏差。

## 10. 行业对标与差距分析（v1.1）

### 10.1 对标基准
| 竞品 | 定位 | 测试体系要点 |
|---|---|---|
| **Azure MCP Server** (microsoft/mcp) | 业界最成熟云 MCP 插件 | 四类测试：Unit(mock)/Live(真资源+bicep)/E2E(全 MCP 协议)/NPX 包测试；**ToolDescriptionEvaluator** 专测工具描述的 LLM 可选择性；自然语言 `e2eTestPrompts.md` 评测集；AOT 兼容、拼写、格式等质量门 |
| **Microsoft MCP 测试最佳实践** | 官方方法论 | 三层模型：Unit(逻辑)→Protocol(MCP 合规)→Agent(LLM 行为)；强调测"发现→选参→解读"全链路 |
| **AWS Agent Toolkit** | 直接对标产品 | skill 激活验证（业界实测发现 Agent 会绕过 skill 直接拼 API——需 rules 文件矫正，激活率是关键指标）；IAM condition key 只读策略仿真；CloudTrail 全量审计；无凭证 docs 检索；沙箱执行隔离 |

### 10.2 差距结论：v1.0 八维 vs 行业必须项
| 行业必须项 | v1.0 是否覆盖 | 处置 |
|---|---|---|
| 安装/卸载/升级生命周期 | ✅ D1 | — |
| 认证/凭证/脱敏 | ✅ D2 | 补 D2-7 无凭证降级 |
| 功能正确性 + 真云 E2E | ✅ D3 | — |
| 安全护栏(审批门/脱敏/拦截) | ✅ D4 | 补 D4-11~14 |
| 多客户端适配 | ✅ D5（且比多数竞品更全：10+ client 矩阵是本规划强项） | — |
| 性能/可靠性 | ✅ D6 | — |
| 跨平台兼容 | ✅ D7 | — |
| 文档/内容质量 | ✅ D8 | — |
| **MCP 协议合规（tools/list schema、JSON-RPC 错误码、传输健壮性）** | ❌ 缺失 | **新增 D9**（Azure 将 E2E 直接定义为"全 MCP 协议测试"，此为行业硬要求） |
| **Agent 行为评测（工具可选择性、skill 激活率、路由准确率）** | ⚠️ 仅 D3-A2 静态路由检查，无真实 LLM 量化评测 | **新增 D10**（AWS 实证：skill 会"静默失效"——Agent 直接绕过；Azure 专设 ToolDescriptionEvaluator；对"引导型"插件这是核心价值指标） |
| **提示注入防护（不可信检索内容）** | ❌ 缺失 | 补 D4-11（Microsoft MCP 安全指南明确要求） |
| **最小权限 IAM 下的可用性仿真** | ⚠️ 部分（D2 报错路径，未做只读凭证全量通过率） | 补 D4-13（对标 AWS condition key 仿真） |
| **Agent 操作可审计性** | ⚠️ 仅测试纪律要求记录，未测产品自身审计能力 | 补 D4-14（对标 AWS CloudTrail 溯源） |
| 供应链/安装期安全 | ⚠️ 仅 npm audit + gitleaks | 补 D4-12（pack 一致性已有 CI，缺 postinstall 审计与 SBOM） |

### 10.3 相对竞品的差异化强项（无需补）
1. **多 Agent 客户端矩阵（D5, 10+ 客户端）**：Azure/AWS 官方测试均只覆盖 4-5 个客户端，本规划 10+，覆盖面领先。
2. **P/G/I 指引来源纪律**：竞品公开资料中未见同等的"引导来源标记"方法论，贴合本插件"引导型"定位。
3. **资源释放审计与环境重置验证（T5/T0）**：竞品 E2E 有自动清理，但"重置为未安装态来验证重装引导"这一被测点为独有。

### 10.4 结论
**v1.0 规划在功能/安全/适配/兼容维度已达行业水准，但在"MCP 协议合规"与"Agent 行为评测"两个行业必备层存在结构性缺口**——恰好对应 Microsoft 三层模型的第 2、3 层。已通过新增 D9/D10 与 D4 四条补强用例闭环，规划升级为 v1.1（10 维度，~207 用例）。
