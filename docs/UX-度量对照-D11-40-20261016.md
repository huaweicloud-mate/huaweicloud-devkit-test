## 一、为什么不用 `dsh --profile headless` 采集

headless 只把**最终 assistant 消息**打到 stdout，不含 token usage 与工具调用痕迹。
本仓实测（2026-10-16）：同一评测集经 headless 采集，`steps` 恒为 0、`tools`/`commands` 全空 → 三指标不可观测。
改为自建 loop 后四项均有真实来源：

| 指标 | 来源 |
|---|---|
| `tokens` | 网关每次响应的 `usage.prompt_tokens + completion_tokens`（真实计费口径） |
| `steps` | MCP `tools/call` 实际调用次数 |
| `fails` | 工具返回 `isError` 次数 + 网关/协议错误次数 |
| `clarifications` | 最终答复命中「追问用户」特征词次数（复用 `ux-metrics.mjs` 口径） |

## 四、口径与边界（勿越界）

- 三指标用于**同 SUT 基线版 ↔ 新版的相对对照**，**不作绝对判定**（换客户端/模型即失效）。
- `clarifications` 与 `fails` 是**特征词近似计数**（见 `eval/harness/ux-metrics.mjs` 的模式表），
  受答复措辞影响；`tokens`/`steps` 为硬计数（网关 usage / MCP 调用）。
- **采样**：本表为**单次采样**（每版 10 条 × 1 次）。`clarifications` 的 Δ=+1 落在特征词计数噪声范围内，
  严格判定（尤其 |Δ| ≤ 1 时）建议 **≥3 次采样取中位**后再比较。

> **后续（2026-10-19）**：已按本建议完成 **3 次采样 × 2 版本** 的复跑，见
> `docs/UX-度量对照-D11-40-三次采样-20261019.md`。结论仍是 `NOT_MET`，但**退化项由 `clarifications` 翻转为 `steps`**
> —— 说明本表的单次采样结论**不可作为判定依据**（依据太薄，不是结论错），本表保留为溯源。
- 本次两版均为**当前已发布状态**（体验缺口尚未修复），故结论是**基线对照**：
  用于验证「无退化」并建立后续改进的对照物；修复落地后应复跑本表。
