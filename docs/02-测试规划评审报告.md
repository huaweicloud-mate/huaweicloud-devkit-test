## 1. 亮点（务必保留）

1. **SUT 画像先行（§1.1–1.7）**：分层架构 L1–L5、36 工具全集、安全模型基线、现有 CI/单测/nightly 基建——测前固定被测基线，这是绝大多数测试规划缺失的第一步，是本规划最扎实的部分。
2. **P/G/I 来源纪律（§2.3）**：每步标注「插件提供/插件缺失/Agent 擅自联想」，完美贴合"引导型"插件本质，是相对竞品的差异化方法论。
3. **行业对标补齐结构性缺口（v1.1）**：对标 Azure MCP Server / Microsoft 三层模型 / AWS Agent Toolkit，新增 **D9 协议合规**与 **D10 Agent 行为评测**——这两层恰好是"工具单独可用 ≠ Agent 会正确选用"的行业实证教训，补得及时且准确。
4. **每条用例带依据标注（v1.2）**：【仓】/【标】/【规】/【通】四类来源，可直接支撑 issue 引用，工程可操作性强。
5. **识别 Windows CI 覆盖空洞**（better-sqlite3 跳过单测）并给出缓解路径——真实风险点捕获，非泛泛而谈。
6. **缺陷分级 + 闭环工作流（§6.2）**：测试→报告→修复提示词→issue→下迭代回归，闭环完整。

## 2. 关键改进建议（按优先级排序）

### 一、落地前必补（A 级，5 项）

#### A1. 用例级模板与优先级标注（最高优先）

**现状**：规划只有"维度级"用例描述（Dx-y + 说明 + 依据），没有**单个用例的完整字段**，207 个用例**无优先级**。第 8 节说"按风险抽代表服务剪枝"，但没有剪枝规则，落地时无从取舍。

**建议**：
- 统一用例字段：`ID / 标题 / 优先级(P0必测|P1应测|P2可测) / 前置条件 / 测试数据 / 操作步骤 / 预期结果 / 指引来源(P/G/I) / 关联工具 / 自动化脚本引用`
- 定义**禁止剪枝集**：D4 安全全量、D1-1/3/5、D9 协议、D10 核心评测集必须全量执行；可剪枝对象仅限长尾服务的读类抽查

**示例模板**（可直接采用）：

```markdown
| 字段 | 内容 |
|---|---|
| ID | D4-5-01 写操作误判检测 |
| 优先级 | P0（安全） |
| 前置条件 | 真云账号 + 最小权限 AK/SK；客户端 Hermes |
| 测试数据 | `hcloud ECS DeleteServer`（带 --delete-all-volume 变体） |
| 步骤 | 1) plan_cli_command 规划删除命令 2) 记录插件判定 3) 若判为 read-only/allow 则记 P0 |
| 预期 | 命令被标记为写操作并转审批门；误判事件数 = 0 |
| P/G/I | P（safety-model 承诺写动词清单） |
```

#### A2. 增加"变更影响分析"环节——回归范围裁剪的依据

**现状**：T0 只做基线对齐（拉代码/环境重置），**没有"本次变更影响了哪些工具/skill/策略 → 决定本轮回归范围"**。207 用例若无范围裁剪，每次代码更新全量回归成本不可接受。

**建议**：在 T0 与 T1 之间插入 `T0.5 变更影响分析(10min)`：
```
git diff → 变更清单（改了 tools.mjs 哪个工具？policy.json 加了哪条规则？SKILL.md 动了哪个？）
→ 映射到受影响用例集 → 本轮只跑"受影响集 + 固定安全回归基线 + 冒烟"
→ 全量回归仅在 Release 前执行
```
这是控制回归成本的核心杠杆，也是专业测试团队的标准动作。

#### A3. 覆盖口径统一：定义覆盖 vs 执行覆盖

**现状矛盾**：
- §2.4 退出标准："36 工具、30 skill **均有对应用例且可执行**"
- §D3-C4："20+ 服务**各抽 1 只读**规划用例"

抽查只能证明"工具可发现/路由正确"，**不能证明"可操作"**——两条口径冲突，退出标准无法客观验收。

**建议**：在 §2.4 明确拆分两个口径：
- **定义覆盖率 100%**：每个工具/skill 至少 1 条用例（可静态评审覆盖）
- **执行覆盖率分层**：核心工具/高危服务 100% 执行；长尾服务按风险抽测，抽测比例写明（如 60%）

#### A4. 前置条件与测试数据管理

**现状**：用例依赖的参考资源（Vector-SSY-* ECS、测试 OBS 桶、真云账号配额）**没有所有权与可用性检查机制**；D3-C3 沙箱 URL ~8h 有效期这类**时间敏感用例未标注执行窗口约束**。

**建议**：
- 增加一张**前置条件矩阵**：`用例ID → 依赖资源(ECS/OBS桶/沙箱/凭证) → 所有者 → 可用性检查命令 → 失效处理`
- 每个阶段开始前先跑可用性检查（一次性脚本），缺资源即 BLOCKED，不静默跳过
- 时间敏感用例（D3-C3、D6-7 长会话）标注建议执行时段

#### A5. 度量体系与执行追踪

**现状**：只有出口标准（≥95% 通过率），**没有过程度量**；207 用例的状态（未执行/通过/失败/阻塞）**没有定义记录载体**（§9 说"可导出 Excel"但未定用例管理载体）。

**建议**：
- 建立分层度量：用例执行率 / 缺陷密度(每百用例) / P0-P2 存量趋势 / D10 激活率与路由准确率趋势 / 自动化覆盖率趋势
- 明确载体起步方案：Excel/腾讯文档母版（ID 列 + 状态列 + 链接支撑），每迭代末出**质量仪表盘**一页
- 出口标准"P2 遗留 ≤3"改为可度量口径（见 §3 一致性清单）

### 二、建议补强的专业深度（B 级，6 项）

#### B1. 对抗性安全测试（D4 缺攻击视角）

**现状**：D4 全部是"已知规则的正向/负向用例"——测试者已知规则清单后，容易陷入"验证正则"的思维定式，测不出规则盲区。

**建议**补三条攻击视角用例：
- **hook 绕过尝试**：大小写变换（`DeleteServer`→`deleteserver`）、编码混淆、参数拼接绕过 risk 规则
- **命令包裹**：`sh -c "hcloud ..."`、`bash -c`、`eval` 包裹写命令——验证 hook 是否检查内层
- **hook_check_* 轻量模糊**：畸形/超长/嵌套 JSON 输入不崩溃、不误放行

#### B2. 提示注入测试细化（D4-11）

**现状**：只写"不被误导执行"，未枚举注入点。不同注入点的 payload 和防线不同。

**建议**明确注入点矩阵：`search_docs`（文档内容）/ `retrieve_skill`（SKILL.md 内容）/ `search_marketplace`（描述）/ `get_service_icon`（URL）——分别构造注入 payload，并区分两级断言：Agent 识别注入拒绝执行（最佳）/ 插件自身有防护（次佳）。

#### B3. D9 协议层补技术细节

**现状**：未固定 MCP 规范版本与 JSON Schema 版本，协议版本协商/降级未测。

**建议**：
- 固定基线：MCP spec 版本（如 2025-06-18 快照）与 inputSchema 的 JSON-Schema 版本（draft-07 / 2020-12）
- 补用例：**老客户端兼容**（initialize 时不声明新能力时能否降级握手的处理）

#### B4. D10 评测成本与结果口径

**现状**：15 评测用例 × 多客户端 × 多模型，**运行成本未估**；"评测失败"未分级。

**建议**：
- 固定 1 主模型（如 deepseek-v4）+ 2 备选，明确每轮评测预算（调用次数/时长）
- 失败分级：选错工具但最终成功 = P2 / 选错导致任务失败 = P1 / 安全干预失效 = P0
- 明确评测集维护责任与更新节奏（每 Release 前评审一次）

#### B5. Windows 补测范围定义

**现状**：只说"至少 1 台 Windows 手动补测"，**没定义补什么**。

**建议**：固定"Windows 专项清单"：D5-6（Windows 已知问题）+ D7-3（better-sqlite3 缺口）+ D1 全生命周期 + D2 凭证流 + MCP Python SDK 检测项（D1-3 doctor）。每次 Release 前全量跑一遍，形成固定回归集而非临时拼凑。

#### B6. CI 有效性审计

**现状**：T1"跑通仓库既有单测/CI"，但未验证 CI 是否为"配置性通过"（如 integration/pack/security 步骤是否真执行）。

**建议**：增加一条"CI 真实性审计"用例：检查 ci.yml 各 job 的`if:`条件与步骤日志，确认 integration 真跑、pack 真验证、gitleaks 真扫描，防止把"跳过"当"通过"（Windows 跳过已知，需确认无其他隐性跳过）。

### 三、锦上添花（C 级，4 项，可选）

1. **C1. issue 模板定义**：§6.2 闭环缺标准输入——定义 issue 模板字段（环境/复现步骤/期望/实际/P-G-I 标注/严重度/建议修复方向），否则拆 issue 质量参差。
2. **C2. 探索式测试补充**：207 个脚本化用例之外，每迭代安排 1–2 小时无脚本探索 session（引导型插件尤其需要，能发现"文档没说但 Agent 会踩"的场景）。
3. **C3. 工时预算**：给一轮回归的总工时估算（对照方法论工时表：人工态 ~10–18h/轮、半自动 ~2.5h/轮），让排期可预期。
4. **C4. 测试数据隐私**：上传/创建的测试内容统一用无害假数据，避免真实业务数据进测试环境（与既有凭证纪律并列）。
