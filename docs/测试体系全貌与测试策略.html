二、测试体系与仓库全景

2.1 架构铁律：用例定义与执行结果分离

整套体系的地基是一对"单一职责"原则：test-cases/ 是纯设计真源（只写"测什么、怎么判"，不含执行态），results/ 是执行结果区（状态、证据、时间戳）。二者由 init_day.py 衔接——复制真源时追加回填列，执行态永不回流污染母版。

这套分离带来的三个好处：用例 ID 永不复用、跨版本趋势可比、执行态不干扰设计演进。它是所有下游脚本（汇总、门禁、提单、度量）的公共前提。

三、测试策略（细节、依据与全面性）

3.1 总体策略：四层金字塔 + 铁律纪律

        ┌ E2E 真云回归 ┐        ← 每晚/迭代门禁，真实凭证，昂贵少量
      ┌─┴ 客户端矩阵集成 ┴─┐      ← 安装/发现/适配 × 10 客户端
    ┌─┴── 功能测试(逐工具) ──┴─┐    ← 39 工具 + 30 skill 原子用例
  ┌─┴── 单元/静态/安全扫描 ────┴─┐  ← test/*.mjs + npm audit + gitleaks
  • 策略要点：下层自动化左移、上层人工/半自动验证。依据：通用测试实践。

测试纪律（铁律）：

  1. P/G/I 来源纪律——每步标 P=插件提供 / G=插件缺失自行解决 / I=Agent 擅自联想（记红线）。贴合"引导型"产品本质，防止测试者凭云知识绕行。依据：设计文档。
  2. 不擅自联想——不猜服务名/操作名/参数，缺能力记缺口。依据：仓库事实。
  3. 凭证纪律——AK/SK 永不进对话/报告，只从本地凭证文件读，输出脱敏。依据：仓库事实。
  4. 写操作纪律——写操作统一走 plan_cli_command → run_approved_command，被误判 read-only 即记安全缺口（高危）。依据：仓库事实。
  5. 资源释放纪律——本轮创建当轮删除 + 只读验证归零，残留即 FAIL。依据：通用测试实践。
  6. 数据隐私纪律——测试数据用无害假数据（demo-<timestamp>），真实业务数据不进环境。依据：通用测试实践。

双口径消除了"抽查=可操作"的矛盾： - 定义覆盖率 100%——39 工具、30 skill、20+ 服务均有对应用例（可静态评审确认）； - 执行覆盖率分层——核心工具/高危服务 100% 执行，长尾服务按风险抽测 ≥ 60%。

禁止剪枝集（任何回归范围裁剪不得触碰）：D4 全量、D1-1/3/5、D9 全量、D10 核心评测集。

3.3 设计策略：六要素 + 列语义 + 源码反推 + 评审闭环

用例质量六要素（每条用例必须同时满足）：

  1. 单一验证点 + 唯一 ID——一个用例只测一件事，ID 一经分配永不复用；
  2. 前置条件明确可复现——写环境/凭证/版本/隔离态，禁用"合适的环境"；
  3. 测试数据具体——写精确输入值/断言契约，不用"若干数据"；
  4. 操作步骤机械执行——编号化，Agent 可直接执行，无"酌情/大概"；
  5. 预期结果可判定 + 唯一断言——用精确错误码/字段/阈值，禁"合理/正确/类"等模糊词；
  6. 关联工具填真实 MCP 工具全名——函数名归"指引来源 源码函数:xxx"。

依据：规范要求 + 通用测试实践。

列语义映射：矩阵每列有唯一语义，内容不得串列（如"关联工具"只填 39 工具/CLI/框架组件，函数名归"指引来源 源码函数:xxx"）。

源码能力反推覆盖（全面性的第二重证据）：不是"想到什么测什么"，而是从 src/*.mjs 反向提取 export 函数/CLI 子命令/环境变量/返回字段，与用例逐一比对。结果：全维度核对出 17 个源码缺口（如 HUAWEICLOUD_DEVKIT_SKIP_UPDATE 环境变量、远程 transport、沙箱分块上传参数、CodeArts 上下文凭证等），已全部落成 16 个新用例（D1-59~64、D2-22~25、D3-C10~12、D4-25/26、D9-10），并同步修正 3 处"设计 vs 实现"漂移（指纹算法 sha256(ak+sk) 无冒号、detect_framework 13 框架非 11 等）。依据：源码函数。

Hermes-Codex 评审闭环：设计稿不"自签合格"——Hermes 产出初版 → Codex 多轮复评（机器可闭合项整改、外部依赖项如实列 status）→ 只有 TEST_DESIGN_READY 才进入执行。归档显示真实走过多轮：ITER-004 评审 8 轮、全量整改 16 轮 prompt。

3.4 执行策略：变更驱动 + 分层 + 双门禁

变更驱动（控制回归成本的核心杠杆）——T0.5 变更影响分析，而非每次全量：

git diff → 受影响用例集映射 → 本轮只跑"受影响集 + 固定安全基线 + 冒烟"
全量回归仅 Release 前

执行分层（防矩阵爆炸）：39 个工具是同一个 Node 进程，不同 Agent 只是不同 MCP 客户端壳，因此按"客户端相关性"分层——工具/协议/性能/兼容/文档层单代表客户端全量；安装+适配层 10 客户端全跑；Agent 行为层代表 3~4 个跨厂商模型。执行量级从 1990 压到 ~360。依据：仓库事实 + 行业对标。

每日流水线 6 步（每个客户端 agent 按 AGENTS.md 自主完成）：

自识别身份 → init_day 建包 → P0→P1→P2 执行+证据落盘
→ 回填状态+时间 → 出八节报告 → 每10分钟提报 → 全量测完统一提单

双门禁防虚报：verify_no_fake_pass.py（标 PASS 必须①实测②证据落盘③evidencePath 回填，否则作废）、verify_coverage.py（P0 必测、NOT_RUN+空 ≤ 15%）。依据：通用测试实践。

自动化闭环：auto-summary workflow 监听 results push 实时刷新 Summary（20:10 北京兜底，防循环 + 单例串行）；sync-to-remote.ps1 每日 20:00 自动同步。

3.5 回归策略：流水线 B + 验证分层 + 防退化

问题单号回归走全链路流水线 B（任意 agent 可自主完成 5 步，不依赖维护者先设计）：

定位(读上游issue+归档用例) → 确认代码真落地(git log -S 防"方案冻结≠已实现")
→ 复现+根因(文件:行号) → 自写回归用例+跑生成器 → 定向复测+回填结论
  • 验证分层（证据强度递增）：函数级探针 → 既有单测 node --test → 真机 SSH。
  • SPEC-MISMATCH 发现法：读方案设计意图对照代码实现找语义冲突（#570 C12 实证：方案"env 三件套真值" vs 代码残留"防 STS 遮蔽"）。依据：开发方案 + 源码函数。
  • 防退化沉淀：P0 回归用例同步进 daily 盯防；核心基线随新需求迭代（NR6）。依据：通用测试实践。
  • 提单纪律：全量测完合并 1 单（不拆单/不逐日/未测完不提）+ 附正式测试报告；复验结论回评上游 issue（已修复则 close）。依据：通用测试实践。

3.6 度量与闭环策略：过程度量 + 退出标准 + 缺陷闭环
