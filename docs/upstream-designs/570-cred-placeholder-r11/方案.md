## 零、一句话结论

「单一事实源」不是把三个文件合并成一个（KooCLI 必须读 `~/.hcloud/config.json`、obsutil 必须读 `~/.obsutilconfig`，删不掉）。

**正确模型：** 凭证值以 `credentials.json`（S1）为权威，S2/S3 只是派生镜像，只能由统一命令生成；用「指纹比对 + mtime 手动改动检测 + 交互仲裁」保证三份永远一致。

**v4 关键决策（本轮新增）：**
1. **配置入口只有一个** —— `npx huaweicloud-devkit auth init`（或市场安装 env 导入）。**禁止指导用户单独配置 KooCLI（S2）**，因为只配 S2 无意义且制造双轨。
2. **受管理 profile = 跟随 current** —— KooCLI 多 profile，devkit 只管理 `current` 档；命名档视为手动配置，只进审计、绝不自动动。
3. **会话内配置优先于 env（R9）** —— devspace 等环境中，众多 agent 的 AK/SK 由平台注入到环境变量（`HW_*`），视为"默认兜底账号"；用户**会话内明确配置/更换**的账号（runtime 或持久化 S1）优先级更高。修改后优先级为：`runtime > S1（含 configuredBySession 标记）> env > S4 > S1`。

## 一、当前架构全部情况

### 1.1 存储层（7 处凭证来源）

| # | 存储 | 内容 | 权限 | 写入者 |
|---|---|---|---|---|
| S1 | `~/.config/huaweicloud/credentials.json`（`HUAWEICLOUD_HOME` 可改 `baseHome`） | `ak/sk/securityToken/region` 明文 | 0600 | `auth init`（`writeGlobalCredentials`） |
| S2 | `~/.hcloud/config.json` | 多套 AK/SK（default + 命名档），`current` 决定生效 | KooCLI 管理（默认 authEncrypt=true 加密） | `hcloud configure set`（`configureHcloud`/`syncAuth`） |
| S3 | `~/.obsutilconfig` | `endpoint/ak/sk/token` 明文 | 0600 | `writeObsConfig` / `setup_obs_config` |
| S4 | Agent MCP 配置（mcp_settings.json 等） | `environment.HW_ACCESS_KEY/HW_SECRET_KEY` | — | 市场安装 UI / DevKit install |
| M1 | MCP 进程内内存 | `ak/sk/securityToken/region` | 进程内存 | `huaweicloud_auth_init`（`setRuntimeCredentials`） |
| E1 | 进程环境变量 | `HW_ACCESS_KEY/HW_SECRET_KEY/HW_SECURITY_TOKEN/HW_REGION` | — | 市场注入 / 启动器继承 / user shell |
| E2 | 沙箱 `/tmp/hw_creds.sh` | STS 临时 AK/SK/SecurityToken | 0600 | `sandbox_credentials` 导出 |

### 1.2 读取链路（两条，互不相通）

```
链路 A：resolveCredentials()  ← 统一入口（credentials.mjs:81-127）
  优先级（v4/R9 调整后）：
    runtime(M1) > S1(configuredBySession 标记生效) > env(E1) > CodeArts(S4) > S1(无标记)
  现状代码（未实施 R9 前）：
    runtime(M1) > env(E1) > CodeArts(S4) > 全局文件(S1)
  特判：env 带 AK+SK+token 且 S1 存在 → 强制 S1 胜出（credentials.mjs:105-117）
  消费方：沙箱 API 签名（hwlink-api.mjs signRequest）、runtime 注入等
  ✗ hcloud 命令不走这条路

链路 B：hcloud 命令
  消费方：runHcloud（MCP 工具）/ bash 手动 hcloud
  读：S2 current profile（KooCLI 7.x 不读 HW_* 环境变量）
  与链路 A 零交集
```

**关键断层点：** 链路 A 的 "env 优先" 只作用于 A 自己；链路 B 只读 S2。而 S2 又是 `auth init` 从 S1 推过去的（且写死 default，不感知 current）→ 双轨由此产生。**R9 修正后**：env 仅兜底，会话内配置（runtime/S1 标记）优先，从源头避免"平台 env 与用户配置"互掐。

### 1.3 写入/同步链路（单向，只有一个方向）

```
auth init（交互输入）               市场安装（MCP UI 填入 AK/SK）
  │  writeGlobalCredentials            │  写入 S4
  │  writeObsConfig                    ▼  注入 MCP 子进程 env
  ▼  configureHcloud                 S4 ──▶ 链路 A 读取
S1 ◀──并写──▶ S2(默认档)、S3
  │
  └── auth sync（幂等重放 S1→S2/S3，只读 S1，不读 env/S4）

方向性：
  S1 → S2/S3   ✅ auth init / auth sync 支持（但写死 default，不感知 current）
  S4/env → S1  ⚠️ 仅通过显式 `auth_switch mode=mcp-config` 时导入，不自动（v5 修正：§1.3 原"不存在"表述过旧，代码已有 mcp-config persist，见 §10.4）
  S2 → S1      ❌ 不存在
  一致性校验   ❌ 不存在（getAuthStatus 只读 S1）
```

### 1.4 诊断链路

```
getAuthStatus（service.mjs:23-34）
  credentialsConfigured ← 只看 S1 是否存在 ak/sk
  obsConfigured         ← 只看 S3 文件存在
  kooCliInstalled       ← 只看 hcloud 命令
  agents                ← 只看 agent 是否注册 MCP

诊断读 S1，实际运行可能走 env/S4 或 S2 → "当前账号"报告不可信
```

## 三、双轨问题根因

**场景：** 市场安装 env 注入账号 A（hwstaff_blue_dev），`auth init` 早先落盘账号 B（hid_5bd08vucufh9）。

```
市场安装 UI ──mcp_settings.json──▶  MCP 进程 env ──resolveCredentials env优先──▶ 链路 A 用账号 A
auth init ──S1──▶ configureHcloud(写 default) ──hcloud 读 current──▶ 链路 B 用账号 B
getAuthStatus 只读 S1 → 报告账号 B（与链路 A 实际生效不一致）
→ 两套账号并存、无仲裁、诊断与运行不一致
```

**核心原因：** 多存储 + 双链路 + 单向同步 + 无一致性仲裁 + 写错档（default vs current）。

## 四、目标架构

```
写入入口（唯一）
  ├─ auth init 交互
  ├─ 市场安装 env（首次导入）
  └─ auth reconcile 交互仲裁
        │  ① 无 HW_SECURITY_TOKEN 才准入
        ▼  ② 首次导入：env 覆盖 S1
S1 credentials.json ⭐ 单一事实源（唯一可手改）
        │  ③ S1 已存在且不同：交互二选一
        ├─ .last_sync 标记（记录上次传播时间，检测手动改动）
        ├─ auth sync/reconcile 幂等传播 S1→S2/S3（刷新 .last_sync）
        ▼
S2 KooCLI（⭐ 只管理 current profile）  S3 OBS 配置
      其他命名档：审计不动
        ▲
getAuthStatus / scan()：指纹比对 + 手动改动检测 + 告警
```

### v4 关键决策 1：配置入口唯一化，禁止单配 S2

只配置 S2 无意义（它是派生镜像，单独配 = 制造双轨；下次 auth sync 会冲掉它）。因此：

**对外指导统一为：「配置凭证只执行 `npx huaweicloud-devkit auth init`，禁止单独配置 KooCLI。」**

需要改动的现状文案：
- `setup-cli.mjs:3729`（install-hcloud 横幅的 `configure init` 备选）→ 删除，只留 `auth init`；
- `tools.mjs:1133`（`runVersionCheck.authHint` 让用户手动 `configure set`）→ 改为指向 `auth init`；
- `tools.mjs:1246`（OBS region 缺失提示手动 `configure set --cli-region`）→ 改为指向 `auth init`；
- skill `huaweicloud-cli-and-auth/SKILL.md:73-75`（`configure init` 标 SAFE）→ 取消 SAFE/DANGEROUS 双档，统一"禁止单独配置 KooCLI，只走 `auth init`"。

### v4 关键决策 2：受管理 profile = 跟随 current（R7）

- 每次 sync 前 `hcloud configure list` 解析 `current`；
- `hcloud configure set --cli-profile=<current> ...` 写入生效档，绝不写 default 落空；
- 选择理由：① 直接对准"实际生效凭证"；② current 语义就是"当前账号"，尊重用户意图、最小惊讶；③ 零副作用、零迁移成本；④ R2 兜底防误伤。专属档 `devkit` 需要改 `current`（全局副作用）且易复现写错档 bug，故不选作默认。

## 五、统一仲裁规则（定稿 R1-R10）【与 1.1.1-next.15 实现一致】

**原则：规则同一，触发频率不同。** 每个存储都用同一判定：是否检测到手动手改（mtime > .last_sync）。

| 规则 | 场景 | 行为 |
|---|---|---|
| **R1**（默认） | S1 存在 | S1 为唯一事实源，向下传播 |
| **R2**（安全阀） | 某存储指纹 ≠ S1 且 mtime 晚于 .last_sync | **不静默覆盖**。已实现：MCP 走 `needs_confirmation` + `confirmToken` 协议，由 `huaweicloud_auth_confirm(decision: s1 \| newImported)` 消费；CLI 走 `cmdAuthReconcile`（非 TTY 守卫，防挂起） |
| **R3** | env 带 HW_SECURITY_TOKEN | 临时 STS 永不落盘（保留 `credentials.mjs` 防遮蔽逻辑）；**加固：`persistCredentials` 对非空 securityToken 直接拒绝** `{status:'error', scope:'rejected'}`（含 mcp-config 通道） |
| **R4** | 某存储指纹 ≠ S1 且 mtime ≤ .last_sync | 纯派生漂移 → 自动按 S1 重写，刷新 .last_sync（runtime 非空时受 R10 抑制） |
| **R5** | 多 profile（--cli-profile） | reconcile 仅管理 **current** 档；命名档视为手动配置 → 只审计不自动动；用户切档需显式交互 |
| **R6** | HUAWEICLOUD_HOME 指向另一份 S1 | reconcile 以当前 baseHome() 为准；迁移需显式 import |
| **R7** | configuredProfileName() / resolveManagedProfile() | 每次 sync 前解析 current；`--cli-profile=<current>` 写入生效档（`configuredProfileName` 委托 `resolveManagedProfile`，缺省回落 `default`） |
| **R8** | 用户切换受管理账号 | 交互式选择某命名档设为 current 并导入 S1 → 传播（显式授权，因为改 current 影响所有 hcloud 命令）⚠️ **设计中，未落地**（对齐 #572：当前仅 sync current 档，无命名档切换实现） |
| **R9** | devspace 平台注入 env（`HW_*`） | env 仅作"默认/兜底"；用户会话内明确配置/更换后提升 S1（`configuredBySession` 标记）优先于 env |
| **R10**（新增，已实现） | runtime 会话凭证有效 | **runtime 非空时禁止一切自动落盘动作**（R4 自动写 / R7 传播）——`syncAuth` 返回 `ok:false 'Runtime credentials are active; auto-sync suppressed (R10)'`；`hasRuntimeCredentials()` 为 runtime-only 门（`runtimeCredentials !== null`），非"任一路径可解析" |

### reconcile 决策流

```
触发（① MCP 启动 / ② auth status / ③ auth sync / ④ 任意 hcloud 前置）
  → scan()：读 S1/S2/S3 + env；解析 hcloud configure list → current 档；生成指纹；比对 .last_sync
  → S1 不存在？ → 是：导入（市场 env / 交互输入）→ 写 S1
  → current 档指纹 = S1？ → 是：结束（其余命名档保持审计）
  → 该文件 mtime > .last_sync？ → 否：自动按 S1 重写 current 档/S3，刷新标记
  → 是：交互二选一（以 S1 为准 / 以手动配置为准导入 S1 再传播）
```

## 七、方案收益

| 原问题 | 解决方式 |
|---|---|
| 同一操作 MCP 与 bash 得到不同账号 | 统一 S1 权威，所有链路收敛 → 两条消费链值相同 |
| bash 看不到 MCP 注入的凭证 | MCP env 在准入时 import 到 S1 再传播；不依赖进程 env 共享 |
| 两份互相不同的明文副本 | 收敛为「1 份权威 + 2 派生镜像」，泄露面下降且一致 |
| 无法确定"当前账号" | `getAuthStatus` 输出三处指纹对照表 + current 档标记，不一致即告警 |
| 手动 hcloud configure 被 auth sync 静默冲掉 | mtime + .last_sync 检测 → R2 交互仲裁 |
| devkit 写 default 而实际生效 current → 账号跳变 | R7：sync 前解析 current，写对生效档；命名档审计不动 |
| 指导用户单独配置 KooCLI（只配 S2）无意义 | v4：配置入口唯一化为 `auth init`，删除所有单配 S2 的指导文案 |

## 八、遗留风险（不在本方案范围，需知悉）

- SK 在 Agent 会话层级（`huaweicloud_auth_init` LLM 传参）与进程 argv（spawn hcloud）中的暴露；
- 多份明文副本无统一轮换/加密（未接入 CSMS/DEW 密钥托管）；
- `hdkitservice` 签名请求 SK 以明文 HTTP Header 传输；
- Windows 无 POSIX 文件权限控制（`ensurePrivateMode` 在 win32 直接 return）。

## 附、第 8 类（env 继承）专项：R9 定稿

**场景**：devspace 中安装的很多 agent，其 AK/SK 均由平台注入到进程环境变量（`HW_ACCESS_KEY/HW_SECRET_KEY`），视为"默认兜底账号"。

**问题**：原 `resolveCredentials` 优先级 `runtime > env > S4 > S1` —— 当用户会话内持久化更换账号（写 S1）时，env 仍然优先，新账号不生效。

**定稿（R9）**：会话内明确配置的账号优先于 env。

```
原优先级:      runtime(M1) > env(E1) > S4 > S1
R9 后优先级:   runtime(M1) > S1(含 configuredBySession 标记) > env(E1) > S4 > S1(无标记)
```

**实现三点**：
1. S1 增加 `configuredBySession: true` 字段，由会话内切换工具 `huaweicloud_auth_switch`（mode=persist）写入；
2. `resolveCredentials` 读取 S1 后，若标记为 true → stored 优先于 env（交换判断顺序）；标记缺失则维持原 env 兜底逻辑；
3. 与既有防遮蔽逻辑（`credentials.mjs:105-117`，env 带 token 时用文件）不冲突，合并为"env 仅在无会话内配置时兜底"。

**提示文案**：切换时告知用户"若 devspace 后续重启会话，env 注入的账号会恢复为平台默认；如需长期固定，请保持会话内切换或同步修改平台配置。"

## 十、会话内切换工具 `huaweicloud_auth_switch`（最终设计定稿）

### 10.1 背景与目的

不是所有 agent 都有 CLI 终端（如 CodeArts Work 客户端），无法直接跑 `auth init` 更换账号。为此设计**会话内**替换凭证的工具，统一走"安全接收 → 临时生效 → 仲裁落盘"三阶段。

### 10.2 输入参数

```jsonc
{
  "mode":   "import" | "memory" | "mcp-config",
  "action": "persist" | "temporary" | "clear",
  "region": "cn-north-4"
}
```

### 10.3 导入文件落点（P1 定稿）

- **路径**：`~/.config/huaweicloud/creds-import.json`（全局，跨 agent/项目）
- **格式**：`{ "ak": "...", "sk": "...", "region": "...", "securityToken": "..." }`
- **处理**：读取后立即擦除（置空/删除）；权限 0600，与 S1 同目录统一管理
- **理由**：凭证属用户级资产，放 `~/.config/huaweicloud/` 与 S1/S3 同源、权限语义统一，不污染项目仓库

### 10.4 行为矩阵（3 mode × 3 action）

| mode | action | 行为 |
|---|---|---|
| import | persist | 读导入文件→擦除→runtime 暂生效→会话内 R2 确认→写 S1（含 configuredBySession）→ sync S2(current)/S3 → 刷新 .last_sync |
| import | temporary | 读导入文件→擦除→仅 runtime，hcloud 不动 |
| memory | persist | 聊天传 AK/SK→同上落盘（**提示 SK 经模型风险**） |
| memory | temporary | 聊天传参→仅 runtime |
| mcp-config | persist | 读 mcp_settings environment→reconcile 导入 S1→传播 |
| mcp-config | temporary | 读 mcp_settings→仅 runtime |
| * | clear | runtime 归零→回退 env/S1 兜底 |

### 10.5 A+C 语义（临时模式边界，已实现）

- `temporary` = **纯内存**，不触 S2/S3 落盘，`.last_sync` 不变；`setRuntimeCredentials(ak, sk, securityToken|undefined, region)`
- `runHcloud` 前置 `runtimeCurrentMismatchWarning()`：`runtime ≠ current档指纹` 时返回 **authWarning 仅提示**（advisory，动态 import 防循环、不阻塞、不改写 result）：
  > "当前 hcloud 使用[旧账号A]，会话内临时账号[新账号B]仅对沙箱/API签名生效；如需 hcloud 也切换请改用 persist。"
- 切换时提示：若 devspace 重启会话，env 注入的账号会恢复为平台默认；运行 `auth init` 会清除 `configuredBySession` 标记。
- **R10 联动**：temporary 后 runtime 非空 → `syncAuth`/自动落盘被抑制，直至 `clear` 或显式 `persist`。

## 九、待测试验证的功能点

### T1（必测）：HUAWEICLOUD_HOME 与 WSL 权限场景

**背景**：WSL 中若 `~` 落在 Windows 挂载盘（`/mnt/c`，drvfs/9p），`chmod 0600` 被静默忽略 → 凭证文件变 0777 世界可读。`credentials.mjs:16-23` 的 `ensurePrivateMode` 会检测到并警告，引导用户 `export HUAWEICLOUD_HOME=$HOME` 把凭证库挪回 Linux 原生盘（ext4）。

**需实测的问题**：
1. `ensurePrivateMode` 在当前 dev 分支是否真的能检测到 drvfs/9p 的 0600 失效（而非误报）？
2. `HUAWEICLOUD_HOME=$HOME` 后，`baseHome()` 是否如预期指向 `/home/<user>`，S1/S3 是否在 correct 目录生成且权限为 0600？
3. **副作用确认**：`HUAWEICLOUD_HOME` 只影响 devkit 自身文件（S1/S3/proxy config/agent registration 检查），**不影响 S2 `~/.hcloud`（由 KooCLI 管理，位置固定）**。需实测确认「S1 换目录、S2 仍留在 `~/.hcloud`」时 `scan()` 的路径映射是否正确，避免对比时漏掉 S2 进而误判一致。
4. `HUAWEICLOUD_HOME` 变更后，重新运行 `auth init` 是否会创建一套全新的 S1 而留下旧库（两套凭证库并存）？

**预期结论**：该功能点真实场景仅局限于 WSL 权限修复；R6（`reconcile` 以当前 `baseHome()` 为准、跨库迁移需显式 import）作为防御性设计保留。

### T2（必测）：KooCLI `configure list` / `configure set --cli-profile` 行为（R7）

**需实测的问题**：

## 十一、R11 占位符/脱敏值归零（#570 修复）

**问题**：#570 中码道 IDE 市场安装把 `<HW_ACCESS_KEY>` 等占位符写进 mcp_settings env，被 `resolveCredentials` 当成有效凭证（truthy），遮蔽 S1 中用户真实凭据，导致"连接成功但云操作全失败"且指纹诊断误导（env 指纹 89302ef5 竟是占位符哈希）。

**规则（R11）**：任一凭证来源（env/S4/S1）的值若呈「模板/占位符形态」→ 一律视为未填（置空），不参与 R9 优先级与指纹比对，并对外输出显式告警。

**占位符判定（`isPlaceholder()`）**：
| 形态 | 示例 | 处理 |
|---|---|---|
| 尖括号占位 | `<HW_ACCESS_KEY>` / `<your-ak>` | 归零 |
| 模板插值 | `${HW_ACCESS_KEY}` | 归零 |
| 关键词占位 | `YOUR_AK` / `REPLACE_ME` / `change.me` | 归零 |
| **脱敏值** | `abc****`（SK 前3位 + 星号，码道分支回写产物） | 归零（非明文有效 SK） |
| 否定式保护 | 真实 AK/SK 为 ≥20 位纯字母数字，无上述符号 | **视为真值，不归零** |

**应用点**：`credentials.mjs` resolveCredentials 的 env（L102-105）/ S1（L114-120）/ CodeArts S4（L195-196、L218-219）四处入口统一归一；`scanState` 对占位符输出 `null` 指纹 + `envIsPlaceholder:true`。

**安全属性**：幂等、对其他 agent 零影响（真值不命中）、对 devspace 零影响（平台注入真值不命中）。必须**先行于**三件套门，否则"占位符三件套"会被误判为平台注入（见 §十二 ②）。

## 十二、码道代理（codearts / codearts-work）凭证处理分支 v5

### 12.1 最终判定流程（冻结）

```
resolveCredentials()
  ① R11 归零先行（占位符/脱敏值 → 置空）
  ② env 完整真三件套门：env 中 AK+SK+HW_SECURITY_TOKEN 三个都非空真值？
       → 命中 = 平台注入（devspace / 华为云在线沙盒）→ 直接用 env 兜底，不进入码道分支
              ↑ devspace 沙盒为官方环境，临时 AK/SK 过期自动更新，平台账号即合法长期账号，无需特殊处理
       → 未命中 = 本地场景（码道市场安装的「AK/SK 两个占位符 + 无 token」天然落空）
  ③ 码道分支（仅本地 + 码道上下文 + 凭证未就绪）：
       S1 权威 + 场景1-4 引导 + 仅 AK/前缀马赛克回写 S4
       其他 agent → 原 R9，一行不改
  ④ 改号通道：仅「会话内切换并持久化」（configuredBySession 标记）能覆盖 env；
      `auth init` 清除标记后 env 恢复优先，不能覆盖 env。
```

**关键事实**（2026-09 实测确认）：
- 码道 IDE 市场安装：env 写 **AK/SK 两个占位符、无 token** → R11 归零 + 三件套门不命中 → 落本地；
- devspace/在线沙盒启动：环境注入 **AK/SK/token 三个真值**（start.sh 从 JOB_ENV_HW_* 映射）→ 三件套门命中 → env 兜底；
- 本地用户自跑 `--transport remote`：非平台注入，无三件套 → 走②本地逻辑，传输方式非判定依据。

### 12.2 场景 1-4（码道本地，S1 权威）

| 场景 | S1 | env/S4 | 处理 |
|---|---|---|---|
| 1 | ✅ 有值 | — 无值 | 询问「是否使用 S1 账号 X？」→ 同意：外同步 S2/S3 + 仅 AK/前缀马赛克回写 S4；不同意：引导新 AK/SK → 写 S1 → 外同步 |
| 2 | ✅ 有值 | ✅ 有真值 | 询问用哪个（R2 仲裁）→ 选定后先写 S1 → 外同步 S2/S3 → 回写 S4 标识 |
| 3 | — 无值 | — 无值 | 引导配置 → 写 S1 → 外同步 S2/S3 |
| 4 | — 无值 | ✅ 有真值 | 确认账号 → 导入 S4 → 写 S1（mode=mcp-config persist）→ 外同步，S4 降为标识 |

### 12.3 S4 回写仅 AK + SK 前3位马赛克

- 码道分支收敛完成后，S4 的 env/environment 块回写：`HW_ACCESS_KEY` = 真 AK；`HW_SECRET_KEY` = **SK 前3位 + 星号**（如 `abc****`），不落完整 SK；
- 理由：S4 为明文配置文件（非 0600 权限），完整 SK 落盘扩大泄露面；前3位泄露不构成风险但可辨识账号；
- 程序端：`isPlaceholder()` 把 `^^[a-zA-Z0-9]{3,4}\*+$` 形态识别为"脱敏值 = 非有效 SK" → `readCodeArtsCredentials`（`ak && sk` 且 sk 非脱敏）不会把它读成有效凭证；
- 方向：单向 S1→S4；防覆盖（已有真值且 ≠ S1 → 走场景 2 询问）；devspace 管理的 S4 豁免回写；
- 说明文案：SK 真实值仅存 S1；`auth status` 输出脱敏尾巴供查看，不落盘。

### 12.4 边界（不影响其他 agent）

| 三件套门 | 与既有 env+S1 防遮蔽逻辑（credentials.mjs:132-147）同源，仅"平台注入=合法长期账号"场景放行，行为与现状一致 |

| `readCodeArtsCredentials` key 宽容匹配 | 只影响 `.codeartsdoer`/`.codeartswork` 两个路径 |
| 改号通道 | `auth_switch persist` 为唯一覆盖 env 的通道，各 agent 通用 |
