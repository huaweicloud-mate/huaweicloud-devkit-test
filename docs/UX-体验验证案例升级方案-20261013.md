## 一、v2 的两个根本弱点

### 1.1 弱点一：断言停留在"文字存在性"

v2 的判据是"返回里有没有中文字符""有没有 `action` 字段"。**开发者可以用一句写死的中文糊弄过去**——断言过了，体验没变。

### 1.2 弱点二：**自证**（断言与被测对象同源）

11 条用例断言 `effective.source == "runtime"` / `persistsAfterRestart == false` 等**工具自己新报的字段**。这是"用被测对象的话证明被测对象对"——**自证**，不构成独立验证。体验的终点不是"字段对了"，而是"**任务真的成功了**"。

## 二、四条范式升级（v3 核心）

| # | 范式 | 做什么 | 为什么更强 | 判据形态 |
|---|---|---|---|---|
| **①** | **闭环有效性（Closure Efficacy）** | 断言"返回里有 action" → **执行该 action，断言症状消失** | 把"提示对不对"变成"提示管不管用" | 夹具 exit 0 |
| **②** | **回放差异分类（Replay Diff）** | 复用 `eval/replay/compare.mjs` 的语义分类，把体验做成"基线 → 分类" | 体验从"每次人工看文案"变成**可量化趋势**，与 21.4% MISS 基线同一套机制 | 分类 CSV + 趋势 |
| **③** | **独立可观测面双轨断言** | 不用工具自述自证：**调一次真云只读 API，从响应体反推账号/资源状态** | 自述字段只做快速回归，独立观测面做金标准；两轨结论必须一致 | 双轨对照表 |
| **④** | **度量对照（Metric With Baseline）** | 同任务跑基线版 ↔ 新版，比 **步数 / 失败次数 / 求助次数** 三指标 | 唯一能回答"体验有没有变好"的口径 | 三指标对照，不劣化且至少一项改善 |

### 范式② 需要扩的分类（`compare.mjs` 现有 7 类之外）

| 新分类 | 含义 | 判定 |
|---|---|---|
| `MISLEADING_HINT` | 提示把根因指向错误方向 | FAIL |
| `INTERNAL_JARGON_LEAK` | 面向用户文案出现内部代号（S1/S2/S3/A+C/R2/R9） | FAIL |
| `ENGLISH_RESIDUE` | 中文语境下仍残留英文整句 | FAIL |
| `UNCLEAR_NEXT_STEP` | 错误的 `action` 不是可执行命令，或缺 action | FAIL |

## 三、三类专项矩阵（可判定、可执行）

### 3.1 误导性归因矩阵（Misleading Diagnosis）

体验里最伤人的不是"报错"，是"**报错指向错误方向**"。已知四例（均有据）：

| # | 场景 | 当前误导 | 正确归因 | 依据 |
|---|---|---|---|---|
| 1 | region 缺失 | 报 `缺少必填参数 cli-domain-id` | 凭证/region 未配 | `SKILL.md:151` 已记录 |
| 2 | 占位符遮蔽真实凭证 | 报"连接成功"但云操作全失败 | 凭证未配置 | issue #570 |
| 3 | KooCLI 未安装 | 误报权限不足 | 工具未装 | — |
| 4 | STS 过期 | 误报 AK 错误 | 临时凭证过期 | `parseStsExpiry` |

### 3.2 终端环境矩阵（Terminal / Encoding）

**这条是本次最该补、也最容易踩的**：Node 输出 UTF-8，而 Windows 控制台默认代码页 936（GBK）→ 中文输出极易乱码。我自己在 PowerShell 5.1 上就反复踩过。

| 环境 | 风险 | 可判定判据 |
|---|---|---|
| Windows cmd/PowerShell（cp936） | 中文乱码 | cp936 解码后无 U+FFFD、无乱码序列 |
| 窄终端（40 列） | 关键信息被截断 | "尚未登录 + 下一步命令"完整可见 |
| `NO_COLOR=1` / `TERM=dumb` | 语义靠颜色携带 → 丢失 | 去色后结论仍可辨 |
| `LANG=C` / `LC_ALL=C`（Linux） | 非 UTF-8 locale 乱码 | 无乱码，关键中文可读 |

### 3.3 故障注入矩阵（Fault Injection）

体验的真相在异常路径：超时(挂起 30s) / 429 限流 / CDN 404 / 完全断网 → 断言 **有界等待（≤30s）+ 中文可动作 + 不误导归因**。可复用已有 `d9-9-delay-timeout.mjs` 的延迟注入能力。

## 五、样板已落地并真跑（不是纸面）

**夹具**：`eval/harness/fixtures/d11-36-guidance-closure.mjs`（含"宿主隔离前置门"）

**实测（2026-10-13 12:0x，1.1.7，Node v22.23.2）**：

| 运行 | 结果 | 说明 |
|---|---|---|
| 原生宿主 | `exit 2` `ENV_CONTAMINATED` | 宿主持有 `.config/huaweicloud/credentials.json` + `.hcloud/config.json` + `.codeartsdoer` → **未登录态根本构造不出来** → 整例不可判定（不计入 PASS/FAIL） |
| 隔离宿主（`USERPROFILE`/`HOME` 置空目录） | `pass=3 fail=2` `exit 1` | 可判定，跑出 2 条真实 FAIL |

**隔离态真实 FAIL（即需求缺口实证）**：

| 断言 | 实际 | 期望 | 对应需求 |
|---|---|---|---|
| `D11-36-steps` | `["auth-init"]` —— **缺 `obtain-aksk`**（没有"去哪拿 AK/SK"） | 含 `obtain-aksk` + 登录动作 | UX-R1 |
| `D11-36-no-en` | 顶层 message 仍为英文整句 `Huawei Cloud credentials are not configured…` | 不含英文整句 | UX-R7 |
| `D11-36-closure` | PASS | 按引导完成登录后症状消失 | —（引导本身有效） |

**污染态的额外发现**：宿主被污染时 `steps` 变成 `["write-import","auth_switch"]`（走了码道分支）——**同一场景分支不同**，进一步证明"体验用例必须隔离宿主"，否则判据不可信。

> 这三条结果全部来自真实执行，未做任何修饰。**"评估完成 ≠ 执行"的口径，用可执行夹具兜住。**

## 七、残余边界（不吹）

1. **范式④的基线依赖双版本可跑**（`eval-set-ux.csv` + 双版本）→ 未就绪前该用例只能 `BLOCKED`，不虚报。
2. **范式③需要真云账号**（双账号/可失效凭证）→ 部分场景只能函数级 fixture 替代，须在证据里标注"非独立面"。
3. **"40 列窄终端不截断"这类判据**仍有人工成分（"关键信息"定义），需在 rubric 里固定关键字段清单。
4. **v2 → v3 不减少用例总数**（35 → 43），但**换掉了判据强度**：从"字段存在"换成"症状消失 / 独立观测 / 指标不劣化"。若仍嫌多，建议只保留 **P1 的 24 条**作为门禁，P2 归为例行巡检。
