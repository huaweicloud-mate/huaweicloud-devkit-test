## 二、闭环规范九类检查

### 1. 需求覆盖与追踪：不通过

`test-cases/tracing/需求-设计-证据追踪表.csv` 实际表头为 10 列：

`sourceAsset, requirementOrRisk, designCaseId, expandedCaseId, testLayer, clientOrOSScope, requiredEvidence, status, owner, gap`

设计级映射 162 行本身均有字段，但这只证明“从设计矩阵生成了 162 行”，没有机器校验需求源资产是否完整覆盖、`designCaseId` 是否能严格连接设计级真源、`expandedCaseId` 是否能严格连接展开级真源。当前只有 20 个设计用例具有展开级映射，其他 142 行使用“无(不展开/代表执行)”，且该结论没有逐需求的判定规则或证据。

专项行中明确存在以下未闭合内容：

- `ITER-005` P2 通用 MCP 白名单接入无对应设计级 ID，gap 为“建议回填”；
- `D2-20` 为 `SPEC(待核对)`；
- `D4-22/23` 为 FAIL 缺陷；
- 其他专项行标为执行记录或复用既有 ID，不能等价于完整需求到证据追踪。

因此不能宣称需求到用例到证据追踪率 100%。

### 2. 测试层次：部分通过

新增 9 条用例分别覆盖安装生命周期、认证、真云功能、安全审批、性能/MCP 协议，层次方向正确。展开级也区分设计基线与 NR3 执行结果。

但 D1-57 的回滚仍主要依赖手工降级命令；D6-8/D9-9 的夹具与真实 MCP/客户端链路没有形成正式可执行证据入口。对于涉及真实客户端、TTY、remote、升级和跨进程的场景，不能用函数/夹具层设计代替端到端层验证。

### 3. 断言强度：不通过

9 条新增用例有明显增强，但仍未满足 Round-09 所要求的“禁止模糊断言”：

- D1-57 没有明确自动回滚/原子切换/备份点的判定；“旧版仍可启动”与“手动降级后恢复”不能证明升级失败已自动回滚。
- D3-C7 使用“如 Ecs.0021 类”以及“错误含可用区域列表或明确 region 错误码”，允许多个未枚举结果。
- D3-C9 使用 `NOT_FOUND 类`、`DELETING-竞态`、`Ecs.0024 或 image config 冻结码`，没有固定错误码、字段路径和 fixture 响应 schema。
- D4-24 使用“TOKEN_EXPIRED 或同义字段”“already_processed 类结果”，未固定唯一错误码/响应字段及 JSON 结构。
- D6-8 使用“timeout 类错误文本”，没有固定错误码或结构化错误字段；内存增量只有记录要求，没有阈值。
- D9-9 使用“如 -32000 或明确 timeout 码”“规范枚举或明确自定义”，仍允许开放式错误码集合；取消分支也没有固定通知、响应或服务端终止证据。
- D2-21 的 `fingerprint(ak,sk)` 没有规定可复现算法/字段格式；“auth_status 显示新凭证就绪”未固定响应字段。

“或同义”“类”“如”“明确”均不能作为唯一机器判定契约。该项为 P1 未闭合。

### 4. 负向路径与恢复：部分通过

安装中断、坏包、过期 token、重复确认、工具超时、协议取消均已进入设计矩阵，场景覆盖有实质改善。

然而 D1-57 缺少自动回滚的可验证动作；D3-C9 的冻结态仍为 SIM fixture；D6-8/D9-9 的超时恢复仍依赖夹具；D4-24 资源计数和重复结果字段没有完全固定。设计覆盖不等于执行闭环，故不能放行。

### 5. 安全与兼容：不通过

D2-21、D3-C7/C8/C9、D4-24 已加入一次性凭证、`tctest-` 标签、清理 owner、企业项目和冻结 fixture 等隔离意图，但真云权限、资源清理、凭证轮换和状态恢复尚未有执行证据。

展开级仍存在：

- `EXP-NR3-09` / D1-39 Windows P0 `FAIL`；
- `EXP-NR3-11` macOS/ARM `BLOCKED`；
- `EXP-NR3-15b` CodeArtsSpace Hook `BLOCKED`；
- `EXP-NR3-16` Linux 升级链 `BLOCKED`；
- `EXP-NR3-20` remote session `NOT_RUN`；
- `EXP-NR3-21` Windows TTY `BLOCKED`。

闭环规范明确要求这些状态未闭合时不得 `TEST_DESIGN_READY`。

### 6. 环境隔离：不通过

新增用例对临时 HOME、一次性 IAM、`tctest-` 资源标签和清理 owner 有明确描述，这是有效补强。但追踪表没有独立的 `cleanupEvidence`、资源句柄或证据链接字段，不能机器确认清理是否完成。

此外，设计级默认规则仍把多个真实云、客户端、OS、跨进程场景归入 `COMMON` 或混合描述，不能证明安装目录、npm cache、registry、凭证文件、真实资源和客户端用户目录逐项隔离。

### 7. 可复现性：部分通过

`gen_matrix.py` 可重生成 162/132 行，设计级和展开级行数、ID、UTF-8-SIG 输出均可复现；NR3 的 `status`、`blockedReason`、`requiredEvidence`、`observedAt` 已拆列，且实际脚本能发现部分状态缺失。

但生成脚本的默认展开规则只在生成输入层提供，脚本没有把每个设计用例的最终代表终端、证据和阻塞项与展开级/追踪表做一致性校验。`gen_tracing.py` 也只是按当前 CSV 生成映射，不检查需求资产完整性、ID 连接完整性或 gap 门禁。

### 8. 多终端覆盖：不通过

NR3 状态漂移在文本层面有所修正，Windows/Linux/macOS、Hook/非 Hook、TTY/非 TTY、remote 均有独立行，这是本轮有效改进。

但展开规则仍不可完整审计：

- 仅 124/162 行含结构化分隔符；
- 38 行仍为“逐客户端”“重点 Windows”“隔离 HOME”等单段文本；
- 结构化行中 23 行以 `真云+代表客户端1` 等非 `COMMON/CLIENT_MATRIX/OS_MATRIX/AGENT_E2E/CROSS_PROCESS` 值开头，且部分行实际是 5 段，不符合声明的四段格式；
- `verify_new.py` 第 56-59 行明确将“非空旧式规则”视为合格，不会阻断上述问题；
- `verify_r10.py` 只统计是否含 `|`，不验证四段结构、枚举类型、代表终端、证据和阻塞字段。

因此“结构化展开规则可审计”未闭合。

### 9. 统计口径与状态：不通过

展开级 NR3 的独立状态列已存在，且 25 行分布与通知一致；`D1-39` 的 Windows FAIL 与 Linux PASS 分开表达，不应简单合并为单一 PASS，这一点可接受。

但存在以下统计缺口：

- 9 条 BLOCKED 行的 `requiredEvidence` 均为空；脚本只要求 BLOCKED/NOT_RUN 有 `blockedReason`，没有要求待补证据独立存在；
- 设计基线 107 行 `status` 为空，追踪表虽标 `UNASSESSED`，两者没有由脚本强制一致；
- 追踪表的状态值混合 `UNASSESSED`、`PASS(ITER-004)`、`PASS(ITER-005)`、执行记录、SPEC 和带缺陷文本，不是统一枚举；
- 同一设计级 ID 可以对应不同终端状态，但没有脚本按 `源用例 + 终端/OS` 校验唯一性与状态聚合规则。

## 四、放行门槛

按 `docs/06-Hermes-Codex测试设计评审闭环.md`，以下门槛仍不满足：

1. 需求到用例到证据追踪 100%：不满足，追踪表有 gap 且无完整机器外键校验。
2. 所有 P0/P1 有可执行且可判定用例：不满足，9 条新增用例仍有开放式断言，D1-57 自动回滚语义不足。
3. 持久化、重启、跨进程：不满足，D1-55 有 SPEC-MISMATCH/NOT_RUN。
4. 多客户端、多 agent、OS、TTY、remote：不满足，存在 BLOCKED/NOT_RUN。
5. 升级命令、同步、重启、回退：不满足，D1-39 为 P0 FAIL，D1-57 未证明自动回滚。
6. 结构化多终端矩阵：不满足，类型和字段不能由脚本严格解析。
7. 版本、环境、证据可复现：部分满足，生成可复现但审计不可阻断，且追踪表没有证据外键核验。

环境类 `BLOCKED`、规格类 `SPEC-MISMATCH`、产品缺陷 `FAIL` 均仍存在。根据用户给定规则，本轮不得给出 `TEST_DESIGN_READY`。
