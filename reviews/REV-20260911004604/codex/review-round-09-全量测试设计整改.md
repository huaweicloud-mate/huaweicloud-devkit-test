## 二、九类检查

### 1. 需求覆盖：不通过

本轮新增的区域、企业项目、资源状态、凭证轮换、安装中断、升级回滚、确认令牌和超时缺口均有正式设计级 ID，新增场景价值成立，且未发现 ID 重复或与单一既有用例完全重复。

但 round-08 要求的全仓 `sourceAsset / requirementOrRisk / designCaseId / expandedCaseId / testLayer / clientOrOSScope / requiredEvidence / status / owner / gap` 追踪表仍未建立。Hermes 报告只在正文口头说明 NR2、NR3、ITER-005 和 hand manual 的归属，不能机器核对，也无法证明需求到用例到证据为 100%。因此需求追踪放行门不成立。

**优先级：P1。**

### 2. 测试层次：通过（附整改项）

新增用例大体区分了函数/夹具、MCP 进程、真云和客户端层；D9-9、D6-8 也明确了协议/工具超时的关联关系。展开级仍保留 NR3 的执行状态，不应把这些状态误读为设计层 PASS。

但 D1-57 的“坏包回滚”只写了可控 registry 注入和手动降级，没有定义被测升级器的原子切换、备份点或回滚契约；D1-56 的“半装状态”也没有固定损坏判定清单。两条用例可作为风险场景，但当前层次定义不足以直接执行并判定实现是否满足产品契约。

### 3. 断言强度：不通过

以下新增用例存在强断言缺口：

- **D1-56**：未规定半装文件清单、安装完成标识、残留锁/配置的判定标准；“完整安装”不可由当前字段直接计算。
- **D1-57**：未规定回滚版本选择、版本切换原子性、坏包缓存清理范围以及“提供降级指引”的具体返回字段/命令。
- **D2-21**：凭证轮换依赖三端真实状态，但未定义旧指纹的可观察位置、最终一致性等待窗口和三端逐项 PASS 条件。
- **D3-C7/D3-C8**：创建真云资源后是否执行、如何清理、区域不可用/企业项目错误时允许的产品结果没有明确错误码或字段级断言。
- **D3-C9**：冻结资源无法稳定构造；“明确报错或可执行指引”是弱 OR 断言，未给出错误分类、指引字段或模拟夹具契约。
- **D4-24**：重复确认的幂等结果和“已处理”响应未定义字段/错误码；令牌 TTL 的边界取值未固定。
- **D6-8/D9-9**：没有固定超时阈值、取消消息/错误码、服务端副作用判定和客户端连接复用的观测协议。D9-9 还把“服务端是否收到取消”写成必查项，但未确认 MCP/JSON-RPC 实现是否支持取消通知。

**优先级：P1。** 每条必须补充字段级、文件/资源副作用、时间窗口和错误码/响应结构断言；不支持的协议能力必须改成明确的能力探测或 `SPEC-MISMATCH`，不能假定存在。

### 4. 负向路径：通过（新增覆盖成立，执行仍未闭合）

安装中断、坏版本、资源不存在/删除/冻结、令牌过期/重放、工具超时和协议取消均已进入设计级矩阵，弥补了 round-08 指出的主要场景缺口。

不过设计覆盖不等于执行闭合。D3-C9 的冻结状态、D6-8/D9-9 的后端挂起夹具、D1-57 的坏 tarball 均未提供可复用夹具或证据入口，需在下一轮补齐。

### 5. 安全与兼容：不通过

D4-24 的过期令牌和重复确认方向正确；D2-21 也保留了旧凭证失效和指纹残留风险。但本轮仍存在：

- NR3 终端展开中的 P0 D1-39 为 `FAIL`；
- Windows/Linux/macOS、Hook/非 Hook、remote、TTY 的未执行项仍未闭合；
- 设计规则默认值把 D2 统一写成“真云+代表客户端1(COMMON)”，不能满足凭证、客户端落点和跨进程状态需要时的覆盖要求；
- D3-C8/D3-C9 涉及真实云项目和冻结资源，但没有在正式追踪资产中列出 owner、清理方案和证据级别。

### 6. 环境隔离：不通过

`D1-56` 使用临时 HOME，方向正确；但 D1-57、D2-21、D3-C7、D3-C8、D3-C9、D4-24 均依赖真实 registry、凭证、资源或审批流，矩阵只写“真云/可控”而未给出隔离目录、一次性账号、资源标签、清理责任和失败后的恢复方案。D6-8/D9-9 的夹具也未在正式资产中固定。

### 7. 可复现性：部分通过

`gen_matrix.py` 的计数、固定本轮 ID、`EXPAND_DEFAULT`/`expand_rule` 和 UTF-8-SIG 输出使 CSV 可以由脚本重生成；新增 9 条记录与脚本定义一致。

仍有两个缺口：

1. 默认展开规则只是按维度填充自然语言字符串，不能生成对应的展开级行，也没有 `requiredEvidence/status/blockedReason` 等矩阵字段，无法单独证明每条用例的代表终端和证据要求。
2. `verify_new.py` 只打印核查结果，不返回失败退出码；`scan_gaps.py` 仍输出“115 条中的”旧文案，且是关键词扫描，不是可阻断的全量审计。脚本可重生成不等于审计失败可自动发现。

**优先级：P1。**

### 8. 多终端覆盖：不通过

已有 NR3 展开级矩阵保留了 Windows、Linux、macOS/ARM、Hook/非 Hook、remote、TTY 等分类，状态没有被伪装成 PASS，这是正确的。但当前仍有：

- macOS/ARM `BLOCKED`；
- CodeArtsSpace Hook 客户端 `BLOCKED`；
- TTY `BLOCKED`；

- D1-39 Windows P0 `FAIL`；

闭环规范明确要求这些状态未闭合时不得放行；本轮没有新增终端证据或产品决策，因此多终端门槛不成立。

### 9. 统计口径：不通过

矩阵中 `BLOCKED`、`FAIL`、`SPEC-MISMATCH` 和 `NOT_RUN` 的文字状态仍被保留，未发现将其计入 PASS 的直接证据；162/132 的设计规模口径也已同步。

但展开级 CSV 没有独立的 `status`、`blockedReason`、`requiredEvidence` 字段，状态被编码在“执行要点/预期结果”文本中；`PASS（46g 为 SPEC-MISMATCH 观测）` 这类同一字段同时表达 PASS 和规格冲突，容易导致机器统计把该行算作 PASS。需结构化状态并拆分结果与观察结论。

## 六、必须整改项

### P0

当前无新增 P0 设计缺口。但既有 D1-39 是 P0 `FAIL`，在正式修复版回归前仍是放行阻断项。

### P1

1. **建立全仓需求→设计级→展开级→证据追踪表**：覆盖 D1-D10、NR2、NR3、NR5、ITER-005 和历史 hand 资产，按 round-08 要求提供字段、owner、status、gap；缺失项逐行列出。
2. **补强 9 条新增用例的可判定契约**：逐条补齐阈值、错误码/响应字段、资源/文件副作用、清理、等待窗口、回滚语义和夹具能力；禁止使用未定义的“明确”“可执行”“正确”“完整”作为唯一断言。
3. **把展开规则变成可审计结构**：每条用例必须有规范展开类型、代表终端/OS/Node/npm/shell/TTY/transport、证据要求、阻塞原因；默认规则只能作为生成输入，不能替代逐用例结果。
4. **修复展开级状态模型**：将 `status`、`blockedReason`、`requiredEvidence`、`observedAt` 独立成列；消除 NR3 旧时间/旧环境描述的漂移，或明确拆分设计基线与执行结果两个真源。
5. **闭合既有阻断项**：D1-39 P0 FAIL；Linux 5 类 BLOCKED；macOS/ARM；CodeArtsSpace；TTY；remote session NOT_RUN；D1-55 SPEC-MISMATCH；以及 4 条既有 Windows SPEC-MISMATCH。每项保留解除条件和证据。
6. **让审计脚本可作为门禁**：`verify_new.py`、`scan_gaps.py` 对缺失 ID、空字段、非空规则、状态混用和工具覆盖失败返回非零退出码，并移除旧的“115 条中的”文案。
7. **补充真实云和凭证隔离方案**：D2-21 使用一次性凭证；D3-C7/C8/C9 明确资源标签、项目/区域、冻结态夹具或模拟级别、清理 owner；D4-24/D6-8/D9-9 明确隔离 HOME、夹具和副作用回收。
