## 发现的缺陷（待上游提单）

### #1【P1】mcp-server.mjs 收到畸形 JSON 后进程崩溃（未返回 -32700）

- **现象**：向 stdio 发送畸形 JSON（`{ not valid json !!`）后，服务进程直接退出（exit code 1），未返回 JSON-RPC `-32700 Parse error`。
- **根因**：`plugins/huaweicloud-core/src/mcp-server.mjs` `parseContentLengthFrame` 中 `JSON.parse(body)`（L152）无 try/catch；异常穿透 `socket.on('data')` 处理器导致进程崩溃。LF framing 路径的 `JSON.parse(line)`（L131）同病。
- **影响**：任意 MCP 客户端发送损坏帧即可杀死服务进程（健壮性/可用性风险）。
- **断言依据**：D9-2 期望「-32700/-32600/-32601/-32602/-32603 错误码规范，客户端可处理」；D9-5 stdio 传输健壮。
- **证据**：`evidence/d9-d3-function/probe.stdout.log`（`FINDING mcp-server 收到畸形 JSON 后进程崩溃 exitCode=1`）。

### #2【P2】未知方法/非法请求一律返回 -32603（未区分 JSON-RPC 错误码）

- **现象**：
  - 未知方法 `completely/unknown_method` → 返回 `-32603`（`Unsupported method`），应为 `-32601 Method not found`；
  - 缺 `method` 的请求（`{jsonrpc,id,params}`）→ 返回 `-32603`，应为 `-32600 Invalid Request`。
- **根因**：`handleMessage`（mcp-server.mjs L161-173）用单一 try/catch 包住 `dispatch()`，把所有 dispatch 抛错统一映射为 `-32603`（L169），未按 JSON-RPC 2.0 区分 `-32600/-32601/-32602`。
- **影响**：客户端无法据此区分「方法不存在」与「内部错误」，违背 JSON-RPC 2.0 错误语义（设计用例 D9-2 明确要求）。
- **断言依据**：D9-2「错误码规范，客户端可处理」。
- **证据**：`evidence/d9-d3-function/probe.stdout.log`（-32601/-32600 两行 FAIL 均返回 code=-32603）。
