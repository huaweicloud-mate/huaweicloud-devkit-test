## 一、【P0 反馈】vendor gate 致 serviceCatalog 路由准确率 78.6% → 0%

**现象**：`huaweicloud_service_catalog` 未传 `vendorConfirmed` 直接抛异常，返回「Vendor gate: this tool operates on Huawei Cloud…」而非路由推荐。评测集 15 条中文意图（"帮我查云主机 / 建 2C4G / 领代金券"等）**全部 MISS，准确率 0%**（v1 基线 78.6%）。

**落点**：`plugins/huaweicloud-core/src/vendor-gate.ts`
- `VENDOR_GATED_TOOLS`（:38）管辖 14 个 cloud 工具（auth 系列 / service_catalog / plan_cli_command / run_* / check_cli / list_regions / sandbox_connect / voucher 系列等）
- `enforceVendorGate()`（:93-96）：`vendorConfirmed` 非「非空字符串 quote」即 throw
- 首次调用触发 once-per-session challenge（:99-101，需 retry 一次）
- `:89` 注释：`boolean true` 不行，必须是「用户确立华为云的原文引用」

**测试侧判断**：这是**有意的安全增强**（防 LLM 把用户模糊需求臆测成华为云任务，源码注释表明历史 0/5 用户从不主动确认）。但副作用显著：**用户不明确说出「华为云」三字（或 hcloud 产物/region ID 等依据），插件对所有云端请求装死**。

**请裁决**：
1. gate 触发条件是否过严？能否放宽为「仅对写操作/建删资源类工具 gate，只读类（list/status/service_catalog 路由）免 gate」？
2. 评测集/真实 agent 会话如何「建立 vendor 确认」才不打断用户？需否 SDK 层提供更顺滑的确认机制（而非依赖 LLM 先问一句）？

**连锁影响**：`plan_cli_command` 被 gate 拦 → `classification.decision=undefined` → 依赖 `decision==='allow'` 触发 `run_approved_command` 的真云 E2E 建删资源链路整体断掉。

## 二、【P0 确认】mcp-protocol `dispatch` API 删除，无向后兼容层

**现象**：v1 的 `mcp-protocol.mjs` 导出单一 `dispatch(method, params, opts)`，v2 删除，重构为 `createDevkitMcpServer` / `createLinkedDevkitServers` / `runInitializeSideEffects` / `normalizeToolCallParams` 工厂函数。源码（mcp-protocol.ts:205 附近）明说「the legacy dispatch held...」，确认主动移除、无兼容 shim。

**影响**：按旧 `dispatch` API 集成的第三方（或测试探针）会静默断链（`mp.dispatch is not a function`）。

**请确认**：是否需在 v2 提供旧 `dispatch` 的兼容导出（标记 deprecated）；还是确认「v2 是 breaking change，不做兼容」？

## 三、【P1 反馈】remote transport 升级 Streamable HTTP，旧 HTTP 客户端需适配

**现象**：`startRemoteServer` 仍用 `node:http` 标准 server（端口 9528 等语义未变），但 transport 升级为 MCP SDK 的 `WebStandardStreamableHTTPServerTransport`。实测：HTTP POST 只带 `Accept: application/json` → **406 Not Acceptable**（要求同时 `application/json, text/event-stream`）；带双 Accept 头 → 200 OK。

**影响**：v1 时代的 remote HTTP 客户端（按「无状态纯 JSON POST」契约写）在 v2 下会 406。属 MCP 规范升级（Streamable HTTP）。

**请确认**：是否属「文档需明示的 breaking change」；是否要求客户端回带 `Mcp-Session-Id` 维持 session。
